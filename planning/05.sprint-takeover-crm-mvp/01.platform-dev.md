# Sprint Takeover CRM (MVP) — platform-dev

> Diseño: [../07-modo-humano-takeover-crm.md](../07-modo-humano-takeover-crm.md) (§5, §6, §9)

## Objetivo

Construir el control on/off por chat, los endpoints que consume el CRM, el push de
mensajes al CRM y el envío saliente de texto del asesor, sin romper el flujo actual.

## Reglas del proyecto (recordatorio)

structlog sin f-strings · imports arriba · tenacity para reintentos · rate limit en rutas ·
`logger.exception` en except · type hints + Pydantic · pasar `make check`.

---

## Tareas

### P-1: Servicio `conversation_control`

Archivo nuevo: `app/services/conversation_control.py`

- `get_state(tenant_slug, wa_id) -> ConversationControl` (crea fila default si no existe, `agent_enabled=true`).
- `set_agent_enabled(tenant_slug, wa_id, enabled, advisor=None)`.
- `touch_inbound(tenant_slug, wa_id)` → setea `last_inbound_at=now`.
- `touch_outbound(...)` → setea `last_outbound_at=now`.
- `is_window_open(state) -> bool` y `window_expires_at(state)` usando `WHATSAPP_SERVICE_WINDOW_HOURS`.
- Operaciones DB vía el engine SQLModel síncrono envueltas en `asyncio.to_thread` (no bloquear el loop).

### P-2: Servicio `crm_push`

Archivo nuevo: `app/services/crm_push.py`

- `push(event, wa_id, **payload)` → `POST {CRM_WEBHOOK_URL}` con header `X-Signature` (HMAC-SHA256 del body con `CRM_WEBHOOK_SECRET`).
- Reintentos con **tenacity** (backoff exponencial); si falla persistente → `logger.exception` (y opcional: log a archivo/cola para reproceso).
- No-op si `CRM_PUSH_ENABLED=false` o `CRM_WEBHOOK_URL` vacío.
- Fire-and-forget desde el caller (task en background, no bloquear la respuesta a Meta).
- Eventos: `message_in`, `message_out`, `agent_toggled`, `takeover_started`.

### P-3: Router CRM

Archivo nuevo: `app/api/v1/crm.py` (registrar en [app/main.py](../../app/api/v1/../../app/main.py)).
Auth: dependencia `require_crm_key` (ver security-dev). Rate limit en cada ruta.

- `POST /api/v1/crm/conversations/{wa_id}/agent` → body `{enabled: bool, advisor?: str}`; setea flag; push `agent_toggled`.
- `GET  /api/v1/crm/conversations/{wa_id}/status` → `{agent_enabled, last_inbound_at, window_open, window_expires_at, taken_over_by}`.
- `POST /api/v1/crm/conversations/{wa_id}/messages` → body `{type:"text", text, advisor}`:
  1. `set_agent_enabled(false, advisor)` (auto-OFF) + push `takeover_started` (si venía ON).
  2. Validar ventana: si cerrada → `409 {error:"service_window_closed", window_expires_at}`.
  3. `send_text_message(wa_id, text, phone_number_id, token)` con credenciales del tenant.
  4. `touch_outbound` + push `message_out`.
  5. Responder `{wa_message_id}`.

Todos los endpoints resuelven el tenant con `get_tenant_async("odontoking")` (default).
Pydantic models para request/response en `app/schemas/`.

### P-4: Hook en el webhook

Archivo: [app/api/v1/whatsapp.py](../../app/api/v1/whatsapp.py) → `_handle_webhook_payload`

Tras resolver `text_content` y antes de encolar al agente:

1. `await conversation_control.touch_inbound(tenant.slug, wa_id)`.
2. `state = await conversation_control.get_state(...)`.
3. Push `message_in` al CRM (siempre que `CRM_PUSH_ENABLED`).
4. Si `state.agent_enabled is False` → **`continue`** (no encolar, el agente no responde).
5. Si ON → ruta actual (buffer / process_fn) **sin cambios**.

> Nota: el chequeo vive en el webhook (ruta in-process de odontoking). No tocar `worker.py`
> en este sprint (odontoking no usa la ruta broker).

### P-5: Espejo de la respuesta del agente + re-chequeo

Archivo: [app/core/langgraph/odontoking_graph.py](../../app/core/langgraph/odontoking_graph.py) o en el `process_fn` de [whatsapp.py](../../app/api/v1/whatsapp.py)

- **Antes de `send_response`** del agente: re-leer `agent_enabled`; si pasó a `False` (humano tomó control durante el LLM) → **no enviar** y loguear `agent_send_skipped_human_takeover`.
- Si se envía → push `message_out` al CRM (si `CRM_MIRROR_AGENT_MODE`).

> Mantener el cambio mínimo y aislado para no alterar el comportamiento del grafo.

## Criterios de aceptación

- `make check` verde; sin cambios de comportamiento con CRM deshabilitado.
- Toggle persiste; entrante con OFF no llama al agente y sí pushea; `POST /messages` envía y auto-apaga; ventana cerrada → 409.

## Riesgos / notas

- `conversation_control` usa el engine síncrono → SIEMPRE vía `asyncio.to_thread`.
- No loguear `text` a nivel INFO con PII (usar preview corto / DEBUG).
- Idempotencia del push y dedupe por `wa_message_id` → se difiere al sprint Media (Fase D).
