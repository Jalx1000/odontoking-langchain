# Sprint 4 — platform-dev tasks

## Objetivo del sprint

Activar el routing del platform hacia agentes externos via RabbitMQ. El platform debe decidir, por tenant, si procesa el mensaje internamente (legacy `_AGENT_REGISTRY` + `odontoking_graph`) o si lo publica en `wa.{tenant_slug}.messages` para que un agente externo (ej: `06.odontoking-agent`) lo consuma.

Discriminante: `tenant.agent_endpoint_url`.
- vacío / None → ruta interna (comportamiento actual)
- seteado → publish a RabbitMQ

---

## Contexto: contract mismatch

El broker del platform (`app/core/broker.py`) hoy publica:

```json
{"wa_id": "591...", "payload": "{\"text\": \"Hola\", ...}"}
```

El worker del agente externo (`06.odontoking-agent/app/worker.py`) espera formato plano:

```json
{"wa_id": "591...", "text": "Hola", "message_id": "wamid.xxx"}
```

**Decisión arquitectónica (Lead):** aplanar el wire format en TODO el sistema. El broker deja de envolver payload-in-payload. Publisher y consumers usan el mismo dict plano. Razones:

- El doble `json.dumps` no aporta nada (no hay heterogeneidad de payloads en este sistema)
- Cada cambio futuro al schema requeriría tocar dos lados; con un solo dict plano, basta tocar uno
- El worker del platform (`03.agent-production/app/worker.py`) ya lee `payload.get("wa_id")` y `payload.get("text")` planos en su handler — el wrapping era cosmético

Esto afecta: `RabbitMQBroker.publish`, `RabbitMQBroker._process_message`, `RedisStreamBroker.publish`, `RedisStreamBroker._process_entry`, `RabbitMQBroker.dlq_retry`, `RedisStreamBroker.dlq_retry`.

## Tareas

### P-1: Aplanar wire format del broker

Archivo: `app/core/broker.py`

1. `RabbitMQBroker.publish(tenant_slug, wa_id, payload)`:
   - Construir el body como `json.dumps({"wa_id": wa_id, **payload})` directamente.
   - No anidar `payload` como string.

2. `RabbitMQBroker._process_message`:
   - `payload = json.loads(message.body.decode())` ya tiene `wa_id` y `text` planos.
   - Eliminar el paso `payload = json.loads(data.get("payload", "{}"))` y `payload["wa_id"] = wa_id`.

3. `RabbitMQBroker.dlq_retry`:
   - El payload guardado en DLQ ya es el body plano; `json.loads(entry["payload"])` da el dict ya listo.
   - Re-publicar como `await self.publish(tenant_slug, wa_id, {k: v for k, v in raw.items() if k != "wa_id"})`.

4. Aplicar la misma reescritura a `RedisStreamBroker.publish` / `_process_entry` / `dlq_retry`.
   - En Redis Streams el field `payload` era un string; ahora guardamos cada campo del dict como field separado, o serializamos el dict entero bajo un único field. **Decisión:** un solo field `data` con JSON plano del dict completo, para no cambiar el shape de `xadd`. Es decir: `{"data": json.dumps({"wa_id": ..., "text": ..., "message_id": ...})}`.

### P-2: Routing en el webhook

Archivo: `app/api/v1/whatsapp.py`, función `_handle_webhook_payload()`.

Al final del loop, donde hoy hay:

```python
if settings.BUFFER_ENABLED:
    await buffer.enqueue(wa_id, text_content, process_fn)
else:
    task = asyncio.create_task(process_fn(wa_id, text_content))
    ...
```

Cambiar a:

```python
if tenant.agent_endpoint_url:
    # External agent — publish to RabbitMQ
    from app.core.broker import broker
    await broker.publish(
        tenant.slug,
        wa_id,
        {"text": text_content, "message_id": msg.id},
    )
    logger.info("whatsapp_message_published_to_broker", tenant=tenant.slug, wa_id=wa_id, message_id=msg.id)
else:
    # Internal agent — current behaviour
    if settings.BUFFER_ENABLED:
        await buffer.enqueue(wa_id, text_content, process_fn)
    else:
        task = asyncio.create_task(process_fn(wa_id, text_content))
        _background_tasks.add(task)
        task.add_done_callback(_background_tasks.discard)
```

Importante:
- El broker singleton ya está creado a nivel módulo en `app/core/broker.py` (línea 552).
- No bloquear el webhook con `setup()` por mensaje — el agente externo se encarga de declarar su topología al iniciar.
- El `broker.publish` debe ser fire-and-fast (await pero rápido). Si falla, log y devolver 200 igual a Meta para evitar reintentos del lado de WhatsApp.

### P-3: Verificar broker en lifespan

Archivo: `app/main.py`.

El broker ya se instancia en import time (`broker = create_broker()` en `app/core/broker.py`). No requiere `await` para inicializar (la conexión a RabbitMQ es lazy en `_get_connection()`).

Acción requerida:
- Añadir al lifespan un cierre limpio del broker: `await broker.close()` en el bloque de shutdown, después de los demás cierres.

Nota: no llamar a `broker.setup(slug)` aquí — los agentes externos declaran su propia topología.
