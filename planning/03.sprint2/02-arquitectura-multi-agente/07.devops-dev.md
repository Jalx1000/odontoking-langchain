## D-1: Dockerfile (multi-stage)

**Archivo:** `Dockerfile`

**Patron de referencia:** `03.agent-production/Dockerfile`

**Diferencia clave:** El monolito usa single-stage con pip install de uv. El template usa multi-stage para reducir el tamano de imagen y separar claramente la fase de build de la de runtime.

```dockerfile
# ── Stage 1: Builder ──────────────────────────────────────────────────────────
FROM python:3.13-slim AS builder

WORKDIR /app

ENV PYTHONFAULTHANDLER=1 \
    PYTHONUNBUFFERED=1 \
    PYTHONHASHSEED=random

# Install system build deps (needed by psycopg, aio-pika binary wheels)
RUN apt-get update && apt-get install -y --no-install-recommends \
    build-essential \
    libpq-dev \
    && rm -rf /var/lib/apt/lists/*

# Install uv
RUN pip install --no-cache-dir uv

# Install dependencies first (layer cached when only app code changes)
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-install-project

# Copy application code and install the project itself
COPY . .
RUN uv sync --frozen


# ── Stage 2: Runner ───────────────────────────────────────────────────────────
FROM python:3.13-slim AS runner

WORKDIR /app

ENV PYTHONFAULTHANDLER=1 \
    PYTHONUNBUFFERED=1 \
    PYTHONHASHSEED=random

# Runtime system deps only (libpq for psycopg at runtime)
RUN apt-get update && apt-get install -y --no-install-recommends \
    libpq5 \
    && rm -rf /var/lib/apt/lists/*

# Copy the virtualenv from builder (already installed, no rebuild needed)
COPY --from=builder /app/.venv /app/.venv
COPY --from=builder /app /app

# Non-root user for security
RUN useradd -m -u 1000 appuser && chown -R appuser:appuser /app
USER appuser

EXPOSE 8000

# Single worker: the RabbitMQ consumer is async — multiple workers = duplicate processing
CMD ["/app/.venv/bin/uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "1"]
```

**Por que `--workers 1` es obligatorio:** El `AgentWorker` abre una sola conexion RabbitMQ y consume la queue. Si uvicorn levanta multiples workers (procesos), cada uno abriria su propia conexion y procesaria los mismos mensajes en paralelo. RabbitMQ entregaria cada mensaje a un solo consumer (round-robin), pero el estado del agente (connection pool, LangGraph graph) estaria duplicado en memoria sin coordinacion. Un solo worker con concurrencia async es lo correcto para este patron.

**Alternativa para escalar:** Si un cliente necesita mayor throughput, escalar horizontalmente en Railway creando multiples instancias del servicio (no multiples workers dentro de una). RabbitMQ balanceara los mensajes entre instancias automaticamente con su mecanismo de consumer competing.

## D-2: railway.toml

**Archivo:** `railway.toml`

**Patron de referencia:** `03.agent-production/railway.toml`

**Diferencia clave:** El healthcheck va a `/health` (no `/api/v1/health`). El timeout es 120s (no 300s) porque el agente solo necesita conectarse a RabbitMQ + PostgreSQL, no hacer warmup de multiples servicios.

```toml
# agent-template Railway configuration
# Each client agent is a separate Railway service pointing to its fork of this repo.

[build]
builder = "dockerfile"
dockerfilePath = "Dockerfile"

[deploy]
startCommand = "/app/.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8000} --workers 1"
healthcheckPath = "/health"
healthcheckTimeout = 120
restartPolicyType = "on_failure"
restartPolicyMaxRetries = 3
```

**Por que healthcheckTimeout = 120:** Railway espera hasta 120 segundos para que el servicio responda en `/health`. El agente necesita:
1. Conectarse a PostgreSQL y crear el connection pool (~2-5s)
2. Inicializar mem0 AsyncMemory (primera vez crea tablas pgvector) (~10-30s)
3. Conectarse a RabbitMQ y declarar exchanges/queues (~2-5s)
4. Compilar el LangGraph StateGraph (~1s)

En redes lentas o cold starts de Railway PostgreSQL, esto puede tardar 60-90s. El 120s da margen seguro.

**Escalado por cliente:** Para un cliente con alto volumen, crear multiples instancias en Railway (no cambiar --workers). Railway balancea el trafico de entrada y RabbitMQ distribuye los mensajes entre instancias.

## D-4: GitHub Actions CI

**Archivo:** `.github/workflows/ci.yml`

**Triggers:** push a `main` y `dev`. No hace push de imagen — solo verifica que todo buildea.

```yaml
name: CI

on:
  push:
    branches: [main, dev]
  pull_request:
    branches: [main]

jobs:
  lint:
    name: Lint
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install uv
        uses: astral-sh/setup-uv@v4
        with:
          version: "latest"

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.13"

      - name: Install dependencies
        run: uv sync --frozen

      - name: Run ruff lint
        run: uv run ruff check .

      - name: Run ruff format check
        run: uv run ruff format --check .

  typecheck:
    name: Type Check
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install uv
        uses: astral-sh/setup-uv@v4
        with:
          version: "latest"

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.13"

      - name: Install dependencies
        run: uv sync --frozen

      - name: Run pyright
        run: uv run pyright
        env:
          # Dummy env vars so config.py can be imported during type checking
          TENANT_SLUG: ci-test
          WHATSAPP_PHONE_NUMBER_ID: "1234567890"
          WHATSAPP_ACCESS_TOKEN: dummy_token
          RABBITMQ_URL: amqp://guest:guest@localhost:5672/
          POSTGRES_DSN: postgresql://postgres:postgres@localhost:5432/agent_ci
          OPENAI_API_KEY: sk-dummy
          PLATFORM_URL: http://localhost:8000
          PLATFORM_INTERNAL_KEY: ci-key

  docker-build:
    name: Docker Build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Build Docker image (no push)
        uses: docker/build-push-action@v6
        with:
          context: .
          file: ./Dockerfile
          push: false
          tags: agent-template:ci
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

**Notas sobre el CI:**
- El job `typecheck` setea env vars dummy porque `pydantic-settings` valida las variables al importar `Settings`. Sin ellas, pyright falla al importar `app/config.py`.
- El `docker-build` usa GitHub Actions cache (`type=gha`) para no rebuildar layers que no cambiaron.
- No hay job de tests porque el template no tiene tests propios — los tests iran en los repos fork de cada cliente.

## D-5: README.md

**Archivo:** `README.md`

```markdown
# agent-template

Base repository for standalone WhatsApp AI agents in the multi-tenant platform.

Each client agent is a fork of this repo with:
- Client-specific tools in `app/tools/`
- Custom system prompt in `prompts/system.md`
- Their own environment variables and Railway deployment

## Architecture

```
Platform (03.agent-production)
    │ publishes to RabbitMQ
    ▼
wa.{TENANT_SLUG}.messages
    │
    ▼ aio-pika consumer
AgentWorker
    ├─ send_typing_indicator
    ├─ BaseAgent.get_response (LangGraph)
    │     ├─ memory.search (pgvector)
    │     ├─ LLM call (gpt-4o-mini + fallback)
    │     └─ tool_call (client tools)
    ├─ send_response (WhatsApp Cloud API)
    └─ mark_as_read + report_usage (background)
```

## How to create a new client agent

### Step 1: Fork this repo

```bash
# On GitHub: click "Use this template" or fork manually
# Rename to: {client-name}-agent (e.g. kohlberg-agent)
git clone https://github.com/your-org/{client}-agent
cd {client}-agent
```

### Step 2: Add client tools

Create tool files in `app/tools/`:

```python
# app/tools/crm.py
from langchain_core.tools import tool

@tool
def get_appointments(patient_id: str) -> str:
    """Get scheduled appointments for a patient."""
    # ... implementation
    return appointments_json
```

Register tools in `app/tools/__init__.py`:

```python
from app.tools.crm import get_appointments, create_appointment

tools = [get_appointments, create_appointment]
```

### Step 3: Customize the system prompt

Edit `prompts/system.md` with the client's business context and instructions.

Available template variables (filled automatically at runtime):
- `{current_datetime}` — current date and time
- `{tenant_slug}` — the tenant identifier

### Step 4: Configure environment variables

Copy `.env.example` to `.env` and fill in the values:

```bash
cp .env.example .env
# Edit .env with your values
```

Required variables:
- `TENANT_SLUG` — must match the slug registered in the platform admin portal
- `WHATSAPP_PHONE_NUMBER_ID` — from Meta Developer Portal
- `WHATSAPP_ACCESS_TOKEN` — from Meta Developer Portal
- `RABBITMQ_URL` — same URL as the platform (get from lead-dev)
- `POSTGRES_DSN` — dedicated PostgreSQL for this agent
- `OPENAI_API_KEY` — OpenAI API key
- `PLATFORM_URL` — URL of 03.agent-production platform
- `PLATFORM_INTERNAL_KEY` — internal API key (get from lead-dev)

### Step 5: Deploy to Railway

1. Create a new Railway project (or add a service to the existing project)
2. Connect the GitHub repo (`{client}-agent`)
3. Add a **PostgreSQL plugin** to the service — Railway provisions it automatically
4. Copy the `DATABASE_URL` from the PostgreSQL plugin and set it as `POSTGRES_DSN`
5. Add all other environment variables from `.env.example`
6. Railway will auto-deploy on push to `main`

The service will be healthy when `GET /health` returns `{"status": "ok"}`.

### Step 6: Register the tenant in the platform

In the platform admin portal:
1. Create a new tenant with `tenant_slug` matching `TENANT_SLUG`
2. Set the WhatsApp webhook to point to the platform (not to this agent)
3. The platform will start routing messages to `wa.{slug}.messages` automatically

## Project structure

```
app/
  main.py            — FastAPI app + lifespan
  config.py          — All env vars (Pydantic Settings)
  agent.py           — BaseAgent: LangGraph graph
  worker.py          — RabbitMQ consumer loop
  llm.py             — LLM service with retry + fallback
  memory.py          — mem0 + pgvector memory service
  usage.py           — Usage reporting to platform
  whatsapp_client.py — WhatsApp Cloud API functions
  tools/
    __init__.py      — Register client tools here
prompts/
  system.md          — System prompt template
Dockerfile           — Multi-stage build
railway.toml         — Railway deployment config
.env.example         — All env vars documented
```

## Key design decisions

- **Single worker process**: the RabbitMQ consumer is async. `--workers 1` is intentional.
- **Own PostgreSQL**: every agent has a dedicated database for LangGraph checkpoints and pgvector memory.
- **No Redis**: the agent has no Redis dependency. Caching is in-process.
- **WA credentials in env vars**: unlike the platform (which stores credentials per-tenant in DB), each agent IS a single tenant, so env vars are the right place.
- **Best-effort usage reporting**: if the platform is down, the agent continues serving users and logs the failure silently.
